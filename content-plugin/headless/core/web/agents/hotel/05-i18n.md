### 1.2 `next.config.ts` (34 lines) — plugin wiring

```ts
// next.config.ts:1-3 and :32-34  (env/images blocks elided — see 04-data-layer.md §11)
import { NextConfig } from "next";
import createNextIntlPlugin from "next-intl/plugin";

const nextConfig: NextConfig = { /* ... */ };

const withNextIntl = createNextIntlPlugin();
export default withNextIntl(nextConfig);
```

`createNextIntlPlugin()` is called with **no argument**. next-intl then resolves the request config
from its default locations (`./i18n/request.(ts|js)` or `./src/i18n/request.(ts|js)`), which is
exactly where this repo puts it. There is **no `i18n` key inside `nextConfig` itself** — next-intl is
configured entirely through the plugin + `src/i18n/*`.

### 1.3 `src/middleware.ts` — complete, 8 lines of content

```ts
import createMiddleware from 'next-intl/middleware';
import { routing } from './i18n/routing';

export default createMiddleware(routing);

export const config = {
    matcher: '/((?!api|trpc|_next|_vercel|.*\\..*).*)'
};
```

- It is at the **project root** (`src/middleware.ts`), i.e. Next's `src/` middleware convention.
- The matcher excludes `api`, `trpc`, `_next`, `_vercel`, and anything containing a `.` (so
  `/favicon.ico`, `/*.json`, `/images/*` are never locale-negotiated).
- `createMiddleware(routing)` is passed **only** the routing object. No `localePrefix`,
  `localeDetection`, `alternateLinks` or custom `detectLocale` callback is supplied here.
- **No auth, no redirects, no header manipulation.** Locale negotiation only. (Confirmed by
  `01-architecture.md` §5 "Middleware".)

### 1.4 `src/i18n/routing.ts` — complete, 6 lines

> **VARIABLE — never hardcode.** `locales` and `defaultLocale` come from `hotel.config.json`
> (`locales` = first language first, `default_locale` ∈ `locales`). `['en','mn']`/`'en'` below is the
> Tegri Gobi reference example only — substitute the configured values when generating.

```ts
import {defineRouting} from 'next-intl/routing';

export const routing = defineRouting({
  locales: <hotel.config.json "locales">,      // e.g. ['en', 'mn']

  defaultLocale: <hotel.config.json "default_locale">   // e.g. 'en'
});
```

That is the whole file. `localePrefix`, `localeDetection`, `localeCookie`, `alternateLinks` are
**NOT SET IN CODE** — next-intl library defaults apply (see §2.3 and §13).

### 1.5 `src/i18n/request.ts` — complete, 15 lines

```ts
import { getRequestConfig } from "next-intl/server";
import { hasLocale } from "next-intl";
import { routing } from "./routing";

export default getRequestConfig(async ({ requestLocale }) => {
  const requested = await requestLocale;
  const locale = hasLocale(routing.locales, requested)
    ? requested
    : routing.defaultLocale;

  return {
    locale,
    messages: (await import(`../../messages/${locale}.json`)).default,
  };
});
```

- Returns **`locale` + `messages` only**. No `timeZone`, no `formats` → next-intl's `useFormatter`
  would use library defaults (and in fact `useFormatter` is never called — see §5.4).
- The messages import is a **dynamic template import**, so both bundles exist and are lazily loaded.
- `hasLocale` (a next-intl v4 helper) is used instead of `routing.locales.includes(...)`; it also
  handles the case where `requested` is `undefined`/`string[]`.

### 1.6 `src/i18n/navigation.ts` — complete, 4 lines

```ts
import { createNavigation } from 'next-intl/navigation';
import { routing } from './routing';
```

### 1.7 Root layout — `src/app/[locale]/layout.tsx` (123 lines)

The i18n-relevant parts:

```tsx
// layout.tsx:1-4, 14-15
import { NextIntlClientProvider, hasLocale } from "next-intl";
import { routing } from "@/i18n/routing";
import { getTranslations } from "next-intl/server";

// layout.tsx:34-47 — SEO title/description come from the `Metadata` namespace
export async function generateMetadata({ params }: Pick<IPageProps, "params">): Promise<Metadata> {
  const { locale } = await params;
  const t = await getTranslations({ locale, namespace: "Metadata" });
  const title = t("homeTitle");
  const description = t("homeDescription");
  const { metadata } = await useMetadata(title, description, locale);
  return { ...metadata };
}

// layout.tsx:49-63
export default async function RootLayout({ children, params }: {
  children: React.ReactNode;
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;

  if (!hasLocale(routing.locales, locale)) {
    notFound();                                    // invalid locale → 404
  }

  const messages = (await import(`../../../messages/${locale}.json`)).default;
  //      ^^^^^^^^ SECOND, independent import of the same file as request.ts

  return (
    <html lang={locale}>                           // layout.tsx:65
      ...
      <NextIntlClientProvider locale={locale} messages={messages}>   // layout.tsx:106
        <NuqsAdapter><Apollo>...<ConditionalLayout>{children}</ConditionalLayout>...</Apollo></NuqsAdapter>
        <Toaster richColors closeButton />
      </NextIntlClientProvider>
      <ErxesWidget />
```

Two facts worth encoding:

1. **The messages are loaded twice.** `request.ts` loads `messages/${locale}.json` for the server
   (metadata, `getTranslations`), and `layout.tsx:62` loads it *again* to hand to
   `NextIntlClientProvider` for the client. The layout import path is `../../../messages/…` (three
   levels up from `src/app/[locale]/` → repo root). This redundancy is the current state —
   `01-architecture.md` §1 "i18n" flags it.
2. **`hasLocale` guard → `notFound()`** means `/xx/anything` is a hard 404 even before a page runs.

### 1.8 Where the `[locale]` segment lives

- Every page is under `src/app/[locale]/…` (45 `page.tsx` files). There is **no `src/app/page.tsx`**
  and **no `src/app/layout.tsx`** — the bare `/` path only exists as a middleware redirect target.
- The two route handlers, `src/app/api/google-reviews/route.ts` and
  `src/app/api/company-signup/unlock/route.ts`, sit **outside** `[locale]` and are excluded by the
  middleware matcher.

## 2. ROUTING

### 2.1 Supported locales

> **VARIABLE — from `hotel.config.json`.** `locales` (first language first) and `default_locale`
> (∈ `locales`) are required intake fields; the `['en','mn']`/`'en'` below is the reference example only.
> Never hardcode them.

| | |
|---|---|
| Locales | **from `hotel.config.json` `locales`** (reference example: `['en', 'mn']` — `src/i18n/routing.ts:4`) |
| Default locale | **from `hotel.config.json` `default_locale`** (reference example: `'en'` — `src/i18n/routing.ts:6`) |
| URL shape | `/<locale>/<path>` — e.g. `/mn/accommodation`, `/en/tours/abc` |
| Root `/` | redirect by middleware (not implemented in app code) |
| `localePrefix` | **NOT SET IN CODE** (next-intl default applies — see §2.3) |
| `localeDetection` | **NOT SET IN CODE** |
| `generateStaticParams` | **NOT FOUND IN CODE** (repo-wide grep: 0 hits) |
| `setRequestLocale` / `unstable_setRequestLocale` | **NOT FOUND IN CODE** (repo-wide grep: 0 hits) |
| Locale from `searchParams` | **NOT FOUND IN CODE** |
| Locale from cookie/header in app code | **NOT FOUND IN CODE** (`NEXT_LOCALE` never read) |

Consequences of "no `generateStaticParams`, no `setRequestLocale`": with next-intl v4 on the App
Router, a `[locale]` layout/page without `setRequestLocale` is **dynamically rendered** per request.
The locale still flows correctly (middleware → `request.ts`), the app just never opts into static
generation for locale pages. `04-data-layer.md` §8 established that only 4 of the 45 pages do any
server fetching at all; the rest render statically-ish but are still resolved per request because
the layout is async + dynamic.

### 2.2 How a URL is resolved (end to end)

```
GET /mn/accommodation
  → src/middleware.ts  createMiddleware(routing)
      matcher matches ("/accommodation" after the /mn prefix is stripped by the matcher logic)
      locale = "mn"  (from path prefix; falls back to cookie/Accept-Language per library default,
                      then to defaultLocale "en")
  → src/app/[locale]/layout.tsx
      const { locale } = await params          // "mn"
      hasLocale(<configured locales>, "mn") → true   // e.g. ['en','mn']
      messages = await import(`../../../messages/mn.json`)
      <html lang="mn"> <NextIntlClientProvider locale="mn" messages={…}>
  → src/app/[locale]/accommodation/page.tsx
      generateMetadata → getTranslations({ locale: "mn", namespace: "Metadata" })
      default export → <ClientAccommodationPage />   (client component)
        const params = useParams(); const currentLocale = params.locale as string  // "mn"
        useCmsPageDetail("accommodation", currentLocale) → refetch() on locale change
```

The **idiom for reading the locale** appears **49 times** as:

```ts
const params = useParams();            // from "next/navigation"  (116 useParams usages repo-wide)
const currentLocale = params.locale as string;
```

and, in server components:

```ts
const { locale } = await params;       // params is Promise<…> per IPageProps
```

`IPageProps` (`src/types/index.ts:3-6`):

```ts
export interface IPageProps {
  params: Promise<{ [key: string]: string }>;
  searchParams: Promise<{ [key: string]: string | string[] | undefined }>;
}
```

### 2.3 Locale prefix strategy — evidence, not assumption

`localePrefix` is never written down in this repo. The code nonetheless **requires** the `always`
(the next-intl default) strategy, in three independent places:

1. **`src/components/LanguageSwitch.tsx:37`** —
   `const pathWithoutLocale = pathname.split("/").slice(2).join("/")`. For `/en/accommodation`
   `split("/")` is `["", "en", "accommodation"]` → `slice(2)` → `"accommodation"`. Under
   `localePrefix: "as-needed"` a URL like `/accommodation` would produce `[]` → `""` and the switcher
   would navigate to `/mn/` (home), silently dropping the page.
2. **`src/components/ErxesWidget.tsx:18-19`** —
   `pathname.replace(/^\/[a-z]{2}(\/|$)/, "/")` explicitly strips a two-letter prefix, with the
   comment `// Strip leading locale segment (/en, /mn, etc.)`.
3. **`src/containers/auth/current-user.tsx:40-44`** uses the **i18n** `usePathname` (locale-free) for
   `/^\/(login|signup|…)/`, while `src/components/layout/ConditionalLayout.tsx:15` uses the **plain**
   `next/navigation` `usePathname` (locale-prefixed) and matches with `endsWith(...)`/`includes(...)`
   — both only work because a locale segment is always present and is handled explicitly.

**Reproduce:** `localePrefix: "always"` behaviour. (The literal value is not in source — see §13.)

### 3.3 The language switcher — `src/components/LanguageSwitch.tsx` (74 lines)

Rendered from **`src/components/layout/Header.tsx:250,407`** and
**`src/components/layout/SecondaryHeader.tsx:131,228`** (twice per header: desktop + mobile menu).
Full source is already catalogued in `03a-layouts.md` §3.9; the i18n-critical parts:

```tsx
"use client"

import { useParams, usePathname, useRouter } from "next/navigation"   // ← PLAIN, not @/i18n/navigation
import { useState, useRef, useEffect } from "react"
import { ChevronDown } from "lucide-react"

const languages = [
  { code: "en", label: "English" },
  { code: "mn", label: "Монгол" },
]

interface LanguageSwitcherProps { isScrolled: boolean }

export default function LanguageSwitcher({ isScrolled }: LanguageSwitcherProps) {
  const params = useParams()
  const pathname = usePathname()          // "/mn/tours/abc?x=1"  → actually pathname has NO query
  const router = useRouter()              // plain Next router
  const [open, setOpen] = useState(false)

  const currentLocale = params.locale as string
  const currentLanguage = languages.find((lang) => lang.code === currentLocale)
  ...
  const handleLanguageChange = (newLocale: string) => {
    const pathWithoutLocale = pathname.split("/").slice(2).join("/")   // "tours/abc"
    const query =
      typeof window !== "undefined" ? window.location.search.replace(/^\?/, "") : ""

    router.push(`/${newLocale}/${pathWithoutLocale}${query ? `?${query}` : ""}`)
    setOpen(false)
  }

  return (
    <div ref={ref} className="relative">
      <button onClick={() => setOpen((v) => !v)}
        className={`flex items-center gap-1 font-medium text-sm px-2 py-1 ${
          isScrolled ? "text-gray-900" : "text-white"}`}>
        {currentLanguage?.code.toUpperCase()}                     {/* "EN" / "MN" */}
        <ChevronDown className={`size-4 opacity-50 transition-transform duration-200 ${open ? "rotate-180" : ""}`} />
      </button>

      <div className={`absolute right-0 top-full mt-1 z-50 min-w-32 rounded-md border bg-white shadow-md py-1 transition-all duration-200 origin-top ${
        open ? "opacity-100 scale-y-100" : "opacity-0 scale-y-95 pointer-events-none"}`}>
          {languages.map((lang) => (
            <button key={lang.code} onClick={() => handleLanguageChange(lang.code)}
              className="w-full text-left px-3 py-1.5 text-sm hover:bg-gray-100">
              {lang.label}                                         {/* "English" / "Монгол" */}
            </button>
          ))}
      </div>
    </div>
  )
}
```

**Behaviour to reproduce exactly:**

- The trigger label is the **uppercased code** (`EN`/`MN`), not the language name.
- The dropdown lists both languages always; no checkmark; `currentLanguage` only drives the trigger.
- **Path is preserved** (`slice(2)` drops the leading `""` + locale segment).
- **Query string is preserved** via `window.location.search` (raw read, so it survives even though
  `usePathname()` has no query).
- **Hash is NOT preserved** (`window.location.hash` is never read) — `#faq` anchors are lost.
- The dropdown closes on outside click (`mousedown` listener, `LanguageSwitch.tsx:26-34`).
- It uses the **plain** Next router, so `router.push("/mn/tours/abc")` is a normal client navigation;
  because the target already contains the locale, this is correct — but note it bypasses next-intl's
  `router`, so a `localeCookie` write (if the library default is on) happens through the middleware on
  the next request rather than through the helper.
- The button text colour flips with `isScrolled` (white over the hero, `text-gray-900` over a solid
  header) — a `Header.tsx` concern, see `03a-layouts.md` §3.2.

**Bug worth reproducing verbatim or fixing deliberately:** on the bare locale root
(`/en` or `/mn`), `"/en".split("/").slice(2).join("/")` → `""`, so the switcher pushes
`/${newLocale}/` (trailing slash). It lands on home, which is usually right, but the URL gets a
trailing slash.

### 5.2 Server vs client

- **Server (`getTranslations` from `next-intl/server`)** is used almost exclusively for SEO:
  **38 of the 40** call sites are `getTranslations({ locale, namespace: "Metadata" })` inside
  `generateMetadata` of a `page.tsx`. The two exceptions are both page bodies:
  `app/[locale]/forms/[slug]/page.tsx:26` (`namespace: "Forms"`) and

- **Client (`useTranslations` from `next-intl`)** does all UI work — every `"use client"` section,
  every form, every dialog, and (notably) **the zod schemas**, which are `.tsx` files precisely so
  they can call the hook.

## 6. DYNAMIC CONTENT LOCALIZATION (backend / CMS)

### 6.1 Mechanism — a GraphQL `language` variable, nothing else

| Mechanism | Present? |
|---|---|
| `language` GraphQL variable on `cp*` queries | **Yes** — `cms`, `tms`, `rooms`, `forms` |
| `getLocalizedField()` / `pickLocale()` helper | **NOT FOUND IN CODE** |
| `Accept-Language` header | **NOT FOUND IN CODE** (0 hits) |
| `?lang=` / `?locale=` query param | **NOT FOUND IN CODE** |
| `name_mn` / `name_en` / `description_mn` columns | **NOT FOUND IN CODE** (`grep _mn\b|_en\b` → 0 field decls) |
| localStorage/sessionStorage locale cache | **NOT FOUND IN CODE** |

The backend is erxes (see `04-data-layer.md` §1). Locale selection is purely
**"the caller passes `language: <locale>` as a query variable"** — the server stores a `language`
field on CMS objects and filters on it.

Relevant GraphQL definitions (`src/sdk/graphql/cms/queries.ts`):

```graphql
query CpPosts($language: String, $categoryIds: [String], …) { cpPosts(language: $language, …) }
query PageList($language: String, $limit: Int, …)          { cpPageList(language: $language, …) }
query CpMenus($language: String, $kind: String, $webId: String) { cpMenus(language: $language, …) }
query CpPages($language: String)                            { cpPages(language: $language, …) }
query CpPostDetail($id: ID!, $language: String)             { cpPost(_id: $id, language: $language) }
```

(`$language: String` is optional everywhere → `undefined` means "server default", which is
**unverified** — see §13.)

### 6.2 The `useCmsPages` default is `mn`, not `en`

```ts
// src/sdk/queries/cms.tsx:241-254
export const useCmsPages = (language?: string) => {
  const { data, loading, refetch } = useQuery(queries.CmsPageDetail, {
    variables: {
      language: language || "mn",     // ← hardcoded fallback
      limit: 100,
    },
    notifyOnNetworkStatusChange: true,
    fetchPolicy: "no-cache",
  });
  const pages: ICmsPage[] = data?.cpPageList?.pages || [];
  return { pages, loading, refetch };
};

// src/sdk/queries/cms.tsx:256-266  — the filter is client-side
export const useCmsPageDetail = (slug?: string, language?: string) => {
  const { pages, loading, refetch } = useCmsPages(language);
  const page = pages.find((p) => p.slug === slug) || ({} as ICmsPage);
  return { page, loading, refetch };
};
```

So: **one query fetches up to 100 pages in a single language, and the client picks by slug.** If
`language` is ever omitted the code silently requests **Mongolian**, not the default locale.

### 8.2 Fonts and Cyrillic

```ts

const roboto = Roboto({ weight:["300","400","500","700"], subsets:["latin"], display:"swap", variable:"--font-roboto" });
```

**Both are loaded with `subsets: ["latin"]` only — `"cyrillic"` is NOT requested** (0 hits for
`cyrillic` in `src/`). `next/font` emits one `@font-face` per requested subset with a `unicode-range`;
with only `latin`, the Cyrillic code points (U+0400–U+04FF for Монгол Cyrillic) are **not** in the
downloaded woff2, so Mongolian text renders from the fallback stack declared in
`src/app/[locale]/globals.css:26-64`:

```css
body {
  font-family:
    var(--font-roboto),
    ui-sans-serif, system-ui, -apple-system, Segoe UI,
    Roboto, Helvetica, Arial, "Apple Color Emoji", "Segoe UI Emoji";
}
```

(`.font-roboto` and `.font-dm-sans` are identical copies of this stack.) Net effect: **Latin text =
Roboto from `next/font`; Mongolian text = the system's Segoe UI/Roboto/Arial** — visibly different
weight/metrics between the two locales. See §13.

Full font analysis: `02-design.md` §2.1–2.2 (do not duplicate).

### 10.2 Add a new translation key `New thing`

1. **Pick the namespace.** One namespace per UI area, already 48. Consume it with
   `const t = useTranslations("Ns")` (client) or
   `const t = await getTranslations({ locale, namespace: "Ns" })` (server).
   - If it's SEO, add it to `Metadata` following `<page>Title` / `<page>Description`.
   - If it's a toast from SDK code, add it to `commonToastMessages`.
   - If it's a form-validation message, add it to the form's namespace and read it from the zod
     schema factory (`src/lib/schema/*/\*.tsx`).
2. **Add it to BOTH files** with the *same key string*:
   ```jsonc
   // messages/en.json
   "Ns": { "New thing": "New thing" }
   // messages/mn.json
   "Ns": { "New thing": "…" }
   ```
   Skipping one side is how §4.6 happened — the missing side renders the raw key.
3. **Use the English phrase as the key** if the string is user-visible prose (379 of 902 keys do);
   use `camelCase` only for machine-ish strings (`Metadata`, `commonToastMessages`).
4. **Interpolation:** `{name}` … `t("New thing", { name })`.
   **Plural:** `{count, plural, one {… # …} other {… # …}}` … `t("New thing", { count })`.
5. **No codegen, no type augmentation** — there is no `next-intl` `IntlMessages` interface and no
   `global.d.ts` message typing in this repo (**NOT FOUND IN CODE**), so the key is untyped and
   mistakes surface only at runtime.
6. **Verify** both `/en/...` and `/mn/...` render the value, not the key.

## 11. Regeneration Recipe

Ordered steps to rebuild the i18n layer from scratch. Dependencies are noted.

**Step 1 — dependencies.** `package.json`: add `"next-intl": "^4.3.4"` (resolved 4.12.0).
Nothing else is i18n-specific.

**Step 2 — routing config (no dependencies).** Create `src/i18n/routing.ts`, substituting `locales` and
`defaultLocale` from `hotel.config.json` (the values below are the reference example only):

```ts
import {defineRouting} from 'next-intl/routing';

export const routing = defineRouting({
  locales: <hotel.config.json "locales">,        // e.g. ['en', 'mn']
  defaultLocale: <hotel.config.json "default_locale">   // e.g. 'en'
});
```

**Step 3 — request config (depends on 2).** Create `src/i18n/request.ts` exactly as in §1.5.
It must return `{ locale, messages }` and dynamic-import `../../messages/${locale}.json`.

**Step 4 — navigation helpers (depends on 2).** Create `src/i18n/navigation.ts` exactly as in §1.6.

**Step 5 — plugin (depends on 3).** Edit `next.config.ts`: import `createNextIntlPlugin` from
`next-intl/plugin`, wrap the exported config with `withNextIntl(nextConfig)`. Leave
`createNextIntlPlugin()` argument-less.

**Step 6 — middleware (depends on 2).** Create `src/middleware.ts` at the project root exactly as in
§1.3: `export default createMiddleware(routing)` plus the matcher
`'/((?!api|trpc|_next|_vercel|.*\\..*).*)'`. Do **not** add auth logic — this file is locale-only.

**Step 7 — messages (no dependencies).** Create `messages/<locale>.json` (one per configured
`locales` entry) at the repo root with the 48 namespaces in §4.2 and the key shapes in §4.3. Start with the `Metadata` namespace
(56 keys, `<page>Title`/`<page>Description`), then `Header`, `Footer`, `commonToastMessages`, then the
per-page namespaces. Reproduce §4.8's tree for exactness. Both files must have identical key sets.

**Step 8 — root layout (depends on 3, 7).** Create `src/app/[locale]/layout.tsx`:
   - `params: Promise<{ locale: string }>`, `const { locale } = await params`
   - `if (!hasLocale(routing.locales, locale)) notFound();`
   - `const messages = (await import(\`../../../messages/${locale}.json\`)).default;`
   - `<html lang={locale}>`
   - wrap children in `<NextIntlClientProvider locale={locale} messages={messages}>`
   - `generateMetadata` using `getTranslations({ locale, namespace: "Metadata" })` +
     `useMetadata(title, description, locale)` (see §8.3).
   - **There is no `src/app/layout.tsx` and no `src/app/page.tsx`.**

**Step 9 — locale reading idiom (depends on 4).** In every client component use
`useParams().locale as string`; in every server page use `const { locale } = await params`.
Pass `language: currentLocale` into CMS/TMS hooks and `refetch()` on change (§6.3).

**Step 10 — language switcher (depends on 4, 7).** Create `src/components/LanguageSwitch.tsx`
exactly as §3.3 (74 lines) and mount it in `Header.tsx` and `SecondaryHeader.tsx` (desktop + mobile).

**Step 11 — formatting helpers (no dependencies).** Create `src/lib/date.ts` with `MN_MONTHS`,
`formatBookingDate`, `formatShortDate`, `formatToDate`, `parseDate`, `toCalendarDay` (§7.1), and

`Reserve.tsx` / `TimeForm.tsx` / `ErxesFormModal.tsx` / `TourBookingPage.tsx` with
`currentLocale === "mn" ? mn : enUS` and pass it as the `locale` prop of `DatePicker`
(`format(date, "MMM dd, yyyy", { locale })`).

**Step 12 — nav discipline (depends on 4).** Replace all `next/link` imports with

**Step 13 — fonts + SEO (depends on 8).** `Roboto` + `DM_Sans` via `next/font/google` with

Copy the fallback stack from `globals.css:26-64`. Do **not** add `alternates`/`hreflang`/`sitemap` —
they don't exist in the original.

**Step 14 — verify.** `/` redirects to `/en`; `/mn/anything` renders with `lang="mn"`;
`/xx/foo` 404s; switching language preserves path + query; no message key leaks in either locale;
booking bar shows `10-р сар 06, 2026` on `/mn` and `Oct 06, 2026` on `/en`.

## 12. Gotchas & Non-obvious Behaviors

1. **Messages are imported twice per request.** `src/i18n/request.ts:13` and
   `src/app/[locale]/layout.tsx:62` both dynamic-import `messages/${locale}.json` with **different
   relative paths** (`../../messages/…` vs `../../../messages/…`). Editing only one file is impossible
   — they're the same file — but reasoning about bundle size, you must count it twice.
2. **`useCmsPages` falls back to `"mn"`, not to the default locale `en`.**
   `src/sdk/queries/cms.tsx:244`: `language: language || "mn"`. Any caller that forgets the argument
   silently gets Mongolian.
3. **`useCmsPageDetail` fetches up to 100 pages then filters client-side by slug.**
   `cms.tsx:241-266`. It is not a detail query — it re-downloads the whole page list on every
   locale change, then `.find(p => p.slug === slug)`.
4. **The refetch-on-locale-change pattern is manual and easy to forget.** ~15 components do
   `useEffect(() => { refetch(); }, [currentLocale])`. Skip it and the component keeps the previous
   language's content until something else triggers a refetch (Apollo `fetchPolicy` is `no-cache` for
   most of these, so there is no cache to fall back to either).
5. **`language: "en"` is hardcoded in `src/sdk/queries/tms.tsx` at three places** (:28, :54, :83).
   Line 54 is safe-ish because `...variables` is spread *after* it; line 28 (`useTmsTours`) is also
   overridable for the same reason; **line 83 (`getTmsTourDetail`) has no spread and cannot be
   overridden** — server-side tour detail metadata is always English.
6. **`Result` and `ReservationSummary` are near-duplicate namespaces** (42 vs 44 keys, 3 identical
   plural keys). Two files in the same flow use different namespaces for the same string
   (`SelectedRoomsCard` uses `Result`, `ReservationSummary.tsx` uses `ReservationSummary`).
7. **`$$` is a two-slot locale separator, not a list.** `getDisplayName` does
   `const [mnName, enName] = name.split("$$")` — a third language is silently dropped, and a name
   with no `$$` puts the whole string in `mnName` (so `/en` gets `enName || mnName` = the Mongolian
   string… actually the whole string, which happens to be correct).
8. **`getCurrencySymbol`'s English branch is dead.** It takes `(currency, locale)` but 20+ call sites
   pass only `currency`, so `isEnglish` is always `false` and MNT renders `₮` on `/en` too. One site
   calls it with zero arguments.
9. **`LanguageSwitch` loses the hash and mangles the root URL.** `window.location.search` is read but
   `window.location.hash` is not; on `/en` it pushes `/mn/` (trailing slash). It also uses the
   **plain** `next/navigation` router + `usePathname`, not the i18n pair — while nearly all other
   files import `Link` from `@/i18n/navigation`. The mix is deliberate-looking but unprincipled.
10. **`usePathname` means two different things depending on the import.** `@/i18n/navigation` →
    `/accommodation`; `next/navigation` → `/mn/accommodation`. `ConditionalLayout` (plain) and
    `current-user.tsx` (i18n) both work only because their matchers are written accordingly
    (`endsWith` vs `^\/(login|…)`).
11. **`params.locale` is read as `params.locale as string` in 49 places** — no shared hook, no type.
    `IPageProps.params` is `Promise<{ [key: string]: string }>`, so every server page must `await`
    it; every client component must go through `useParams()`.
12. **No `generateStaticParams`, no `setRequestLocale`** → nothing under `[locale]` is statically
    generated from the locale perspective, even though most pages do no data fetching.
13. **`<html lang>` is `"mn"`, which is correct BCP-47 but not the `mn-MN` some tools expect**;
    `openGraph.locale` is passed the raw `"en"`/`"mn"` instead of `en_US`/`mn_MN`.
14. **Fonts only load the `latin` subset** while the primary locale is Cyrillic. Mongolian text
    silently falls back to the system stack declared in `globals.css:26-64`; there is no
    `cyrillic` subset request anywhere. If you "fix" this you change the visual rendering of every
    Mongolian page.
15. **The zod schemas are `.tsx` files because they call hooks.** `src/lib/schema/{appointment,booking,reserve}/index.tsx`
    export `use*` functions that build schemas with `t()`. Refactoring them to `.ts` or moving them
    out of React breaks every form.
16. **`commonToastMessages` is the only namespace imported from `src/sdk/`** (17 files) — including
    pure GraphQL modules like `sdk/mutations/auth.tsx`. Those files therefore must be client-side and
    under a `NextIntlClientProvider`.
17. **`useMetadata` is an async function named `use*`** (`src/lib/hooks/useMetadata.ts:1`) but it is
    not a React hook — it's `await`ed in `generateMetadata`. Lint rules for hooks do not fire because
    the repo disables the relevant rules (see `04-data-layer.md` §7.3). Called from 38 files.
18. **Missing keys render the raw key.** 7 keys are referenced but absent from `en.json` (§4.7) and
    14 keys are asymmetric between the two files (§4.6). `LodgeStaysDetail.Amenities` / `Main
    Activities` / `Itinerary details coming soon` are reachable from code but exist only in `mn.json`,
    so `/en/...` shows the raw key.
19. **Two namespaces are completely dead:** `Additional` and `Memories`. 287 keys total are never
    referenced by a literal `t()` (three call sites use computed keys, so the true number is slightly
    lower).
20. **The `Terelj Resort` brand name survives in `auth-container.tsx`** (lines 91 and 162) — a
    different property's name on the login/signup sidebar, in both locales.
21. **Deal `description` payloads are Mongolian HTML** regardless of locale
    (`useBookingSubmit.tsx:191-196`, `TourBookingPage.tsx:303-315`). Staff read them in erxes; they
    are not UI, so they were never localized.
22. **Middleware matcher excludes anything with a dot** — so `/en/something.json` or a locale-prefixed
    file request bypasses locale negotiation entirely.
23. **`next/link` is never imported.** 56 files import from `@/i18n/navigation`; if you introduce
    `next/link` you break the locale-prefixing contract (hrefs are written prefix-free).

## 13. Open Questions

1. **`localePrefix` / `localeDetection` / `localeCookie` values are NOT IN CODE.** `routing.ts` sets
   only `locales` + `defaultLocale`. §2.3 argues from three call sites that the effective strategy is
   `always`, and `01-architecture.md` §1 states the same, but the literal is a next-intl library
   default, not a repo value. Same for whether an `Accept-Language` cookie is read by the middleware
   (the *library* does this; the *app* never does — 0 hits for `NEXT_LOCALE`).
2. **What does the backend do when `language` is `undefined` or an unsupported value?** All `$language`
   variables are optional `String`. Whether `undefined` means "all languages", "server default", or
   "the portal's primary language" cannot be determined from this repo.
3. **Does the erxes CMS actually carry both `mn` and `en` rows for every page slug?** The client asks
   for one language at a time; if a slug only exists in one language, `page.name` is `undefined` and
   `VideoPageLayout`/`BannerSection` render an empty `<h1>` (they do `page?.name || ""`). Not verifiable
   from source.
4. **Why does `useCmsPages` default to `mn` while `defaultLocale` is `en`?** Either a leftover from a
   Mongolian-first launch or a deliberate CMS-side default. No comment explains it.
5. **Is the missing `"cyrillic"` font subset intentional?** Every Mongolian string renders in the
   system fallback today. Adding `subsets: ["latin", "cyrillic"]` would change metrics/line-breaking on
   ~half the site; the current behaviour may be an accident or a deliberate choice to avoid the extra
   woff2 bytes. **Cannot be determined from source.**
6. **No `hreflang`, no sitemap, no canonical.** Is SEO parity between `/en` and `/mn` a requirement?
   Nothing in the repo suggests it either way.
7. **`openGraph.locale` raw value.** Is the OG locale format (`en_US`) required by any consumer, or is
   the raw code fine? Unverified.
8. **Is `LodgeStays`'s per-locale tour-ID exclusion list still current?** Four opaque IDs are hard-coded
   at `LodgeStays.tsx:39,42,46,49`; no comment explains what they are or who maintains them.
9. **Are the 7 referenced-but-missing keys real runtime bugs?** `Appointment.Continue`,
   `Profile.Saving...`, `Profile.profileDescription`, `Profile.profileTitle` were not found in either
   messages file. If the components that call them are unreachable, they're latent. **Not traced to a
   live render path.**
10. **Are the 287 orphan keys intentionally kept as a translation backlog?** Static analysis can't
    distinguish "dead" from "used via a computed key" (3 confirmed computed call sites) or "kept for
    a future page".
11. **`corepack`/package-manager ambiguity** (carried from `01-architecture.md` §1): three lockfiles
    exist. This analysis used `pnpm-lock.yaml` for resolved versions; if CI uses npm or yarn the
    resolved `next-intl` version could differ (all three declare `^4.3.4`, so any v4 ≥4.3.4 is legal
    and API drift across v4 minors is possible).
12. **Does `router.push` from the plain Next router (used by `LanguageSwitch`) update next-intl's
    locale cookie?** Presumably yes via middleware on the subsequent request, but `localeCookie` is
    not configured in code (see 1), so this depends entirely on library defaults.
13. **Which locale does the erxes chat widget (`ErxesWidget`) use?** It strips the locale segment from
    the pathname (`ErxesWidget.tsx:18-19`) but never passes a language to the widget bootstrap —
    so the messenger is presumably always in its own default. **NOT FOUND IN CODE.**
14. **`getCurrencySymbol(currency, locale)` — is the `en → $` mapping intended?** MNT rendered as `$`
    for English users would be a deliberate localization choice, but no caller passes `locale`, so the
    branch is untested. See §12.8.
15. **Is the Mongolian-only `formatBookingDate` suffix grammar correct?** It produces
    `2026 оны 10-р сарын 6` by string concatenation (`"ын"` appended to `"10-р сар"`), which is a
    hand-rolled genitive. A Mongolian reviewer should confirm; no test covers it.
